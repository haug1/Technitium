# Declarative configuration

The [JSON Schema](technitium.schema.json) describes the proposed version 1 manifest. See the [settings inventory](../DECLARATIVE-SETTINGS-INVENTORY.md) for existing defaults, aliases, validation, and service effects. The [example manifests](examples) show a minimal manifest, named resources, and secret references.

Use `dotnet run --project DnsServerApp/DnsServerApp.csproj -- config validate path/to/technitium.json` to check the manifest's schema and references. This command uses `technitium.json` in the current directory when the path is omitted. Effective settings and platform-specific validation will run against the candidate configuration during planning.

## Ownership and updates

The applied manifest defines ownership. Preview and validation leave ownership and settings untouched. Apply updates ownership only after activation succeeds, and recovery restores the previous ownership together with the last working settings.

| Manifest input | Effective setting after successful apply | Ownership |
| --- | --- | --- |
| Field omitted | Keep the existing value. On a fresh instance, use the server's normal initialization rules. | Unmanaged. Removing a field from a later manifest releases ownership and keeps its last effective value. |
| Explicit scalar or reference | Use the declared value after validation and normalization. | Own the field. |
| `null` on a setting that permits it | Reset to its fresh-config default for the current host without using environment overrides. Optional values with no default become unset. | Own the reset value. |
| Nonempty list | Replace the operator-managed entries in that field. Preserve the sequence when it has meaning. | Own the collection. |
| Empty list | Replace the operator-managed entries with an empty list, then apply the field's existing normalization rules. For example, empty DNS listener endpoints select default endpoints. | Own the collection. |
| Named map with object entries | Create a missing entry or update its declared fields. Unmentioned keys stay in place. Validate required creation inputs against the effective entry. | Own each declared entry's existence and its declared fields. |
| Empty named map | Keep all existing entries. Previously managed keys absent from the map become unmanaged. | Own no entries in that map. |
| `null` at a named map entry | Remove that entry if it exists. Reapplying the deletion is a no-op. | Own the entry's absence until the declaration is removed. |
| `null` on a named map where the schema permits it | Reset the whole map to its default. Include removals in the preview. | Own map membership. |

Named keys use the subsystem's identity rules. Zones and TSIG keys use canonical DNS names, scope names use the DHCP manager's case-sensitive keys, and reservations use normalized MAC addresses within the scope. Users, groups, apps, and permission entries use the identities accepted by their managers. Reject duplicate keys after normalization, even when their JSON spellings differ. A rename is an explicit resource change. Reconciliation preserves runtime-owned data. In a record collection, replicated, generated, and lease-maintained records stay under their existing owners. If the server cannot determine whether an existing record is operator-managed, preview reports a conflict before any mutation.

## Competing writers

Evaluate the entire proposed change against the active ownership policy before calling setters or persistence routines. Reject a mixed request as a unit if any part would change a managed value. An equal normalized value is permitted and skips the managed setter. Report conflicting paths with the response and expose the managed paths for inspection through the settings API and admin console. Changes made by the server's existing runtime and lifecycle operations follow their documented invariants.

| Source | Expected result |
| --- | --- |
| UI or settings API | Unmanaged changes proceed. A change to a managed field or managed resource membership fails before any part of the request takes effect. |
| Backup restore | Compare the selected restore fields against ownership. Apply an allowed restore through the existing manager. A conflict rejects the restore before modifying the selected stores. |
| Cluster transfer | The primary owns cluster-wide declarations. A secondary can declare node-local values. Transfers preserve node-local settings and reject ownership conflicts before changing the selected stores. |
| Cluster bootstrap | Check the current topology against the declared bootstrap intent. A matching initialized role is a no-op. Report an incompatible existing topology as a conflict. |

An explicitly declared value takes precedence over the corresponding existing setting or legacy environment variable. If `DNS_SERVER_DOMAIN=old.example.test` conflicts with declared `dns.serverDomain=primary.example.test`, validation reports the conflict by field and environment-variable name. Local validation checks its own environment. Remote preview and startup report conflicts from the server environment. The declared value is the candidate. Omitting that field preserves the existing domain on an initialized server and lets the normal legacy environment handling supply it on a fresh server. Releasing ownership allows later API changes without restoring an older value.

Zone record owners use full DNS names with an optional trailing dot. Use `@` for the zone apex. Validation checks that each owner belongs to its enclosing zone and reports invalid record types or record data by field. The zone-file data form uses the enclosing zone as the origin for relative names and accepts data for one record per entry.

## Validation examples

| Input | Expected result |
| --- | --- |
| `{"schemaVersion":1}` | Valid. No settings are owned. |
| `{"schemaVersion":2}` | Reject with an unsupported version diagnostic at `schemaVersion`. |
| `{"schemaVersion":1,"dns":{"retryCount":2}}` | Reject unknown field `dns.retryCount`. |
| `{"schemaVersion":1,"logging":{"logQueries":true,"logQueries":false}}` | Reject the duplicate key at `logging.logQueries` before reading the last value. |
| `{"schemaVersion":1,"zones":{"EXAMPLE.test":{},"example.test":{}}}` | Reject the duplicate canonical zone key. |
| `{"schemaVersion":1,"logging":{"retentionDays":null}}` | Valid reset. The retention setting becomes 365 days and remains managed. |
| `{"schemaVersion":1,"dhcp":{"scopes":{"Lab":null}}}` | Preview reports deletion if the scope exists. Apply reconciles that explicit deletion. |
| `{"schemaVersion":1,"web":{"certificate":{"password":{"environment":"MISSING_CERT_PASSWORD"}}}}` | The reference has valid JSON shape. Validation fails when the referenced value is missing and reports `web.certificate.password` without printing secret material. |

Secret references select one environment variable or one file. Resolve relative reference paths from the manifest's directory. A referenced file must contain readable, nonempty UTF-8 text. Resolution preserves the text as written, including trailing newlines. Settings that are server paths, such as a TLS certificate path, use the owning manager's path rules. Preview, diagnostics, and exports report references or missing-input markers and keep resolved values out of their output. Remote proxy preview resolves environment references on the server and requires Settings modify permission for password references. Local `config validate` resolves references in the CLI environment. File references require a local manifest. Standalone servers can apply proxy settings at startup or through the configuration API. Apply verifies the referenced password against the preview revision before persisting changes. An enabled proxy requires an address and port. Clear the password when removing its username. Setting the type to `None` or `null` disables the proxy and clears its connection details. The regular export includes public proxy settings and reports a configured password as a missing input.

Optional DNS listener bindings are declared under `dns.listeners`. Binding changes restart DNS and must bind successfully before persistence. Secure listeners use the loaded DNS certificate. Declare `dns.listeners.certificate.path` to load a PKCS #12 file with a private key. Relative certificate paths resolve from the server’s configuration directory. The optional password uses a secret reference. Unix sockets require an absolute path. Set a Unix socket object to `null` to disable it and clear its path.

DNS certificate preview requires Settings modify permission when a path or password is declared. Preview checks that the certificate and private key can be loaded. Changes to the certificate file or referenced password invalidate the preview revision. The export includes the path and reports a configured password as a missing input. Supply the certificate file separately when migrating. To remove the certificate, set the certificate object to `null` and disable any remaining secure DNS bindings in the same manifest.

The DNS listener policy applies live. Use `dns.listeners.reverseProxyAcl` for ordered proxy trust rules and `dns.listeners.useClientSubnetAsSource` to use ECS as the client source for trusted DNS peers. The `dns.listeners.http.realIpHeader` and `dns.listeners.http.helpRedirect` fields control HTTP proxy requests and the DoH help redirect. An empty or null DNS reverse-proxy ACL trusts no IP-based proxies. A null real-IP header restores `X-Real-IP`.

Web console certificate settings can be previewed with Settings modify permission. Preview checks `web.certificate.path` and its optional password reference against the candidate HTTPS settings. Standalone servers can apply the certificate at startup or through the API. Export includes the certificate path and `web.useSelfSignedCertificate` and reports a configured password as a missing input. Declare `web.useSelfSignedCertificate: true` and `web.certificate: null` to replace a configured certificate with a generated one.

Set `web.rootPath` in a local startup manifest to serve a different web assets directory. Relative paths resolve from the configuration directory, and the directory must exist. A null value selects the installed web root. The last applied override persists across restarts. The settings API can preview the change and report the effective path, while installation and migration of a custom web root require local filesystem access. Inspection export includes the path.

## Previewing changes

Run `dotnet run --project DnsServerApp/DnsServerApp.csproj -- config plan path/to/technitium.json https://dns.example.test` against a running instance. Set `TECHNITIUM_CONFIG_API_TOKEN` to a token with Settings view permission. The command accepts HTTP for loopback development instances.

The current preview covers the DNS server domain, DNS listener endpoints and source networks, authoritative DNS defaults, selected DNS options, web listener addresses, ports, proxy ACL, and headers, logging settings, statistics, blocklist sources and scheduling, and the app auto-update flag. It reports changed field paths, DNS and web restarts, and a revision for the manifest and server snapshot. Values stay out of the response. A service restart invalidates earlier revisions. Zone preview reports primary zone creation, explicit deletion, and enabled-state changes. For primary zones outside catalogs and cluster infrastructure, it also reports changes to query, transfer, notification, and dynamic update modes, network ACLs, and notification name server addresses. It requires permission to view the relevant zones. For primary zones, record preview reports additions and changes to TTL, disabled state, and comments for zone-file, wire-format hex, and base64 TXT data. It preserves generated and DHCP-maintained records and rejects a list that would remove an existing record of unknown ownership. DHCP preview covers scope creation, explicit deletion, enabled state, address range, DHCP options and exclusion changes, and reservation additions, updates, and removals. Reservation keys accept colon- and hyphen-separated MAC addresses. A reservation change cannot conflict with an active lease or another reservation. It requires DHCP view permission. A changed range cannot overlap another scope or exclude an existing active lease, reservation, or exclusion. A scope with active leases cannot be removed. Apply can create primary zones, update their enabled state, and explicitly delete them outside catalogs. On a cluster node these zones stay local to that node. Cluster infrastructure and catalog members are managed by the cluster and cannot be declared here. Zone files, permissions, and ownership commit in the same journal. A declared zone owns its membership, and explicitly declared enabled and policy fields are managed individually. The zone API and backup restore protect managed membership, enabled state, policies, and declared record collections. Omit the record collection from a later manifest to resume editing it through the zone API. Omitting the zone in a later apply releases ownership and preserves its current configuration. Apply also accepts the previewed query, transfer, notification, and dynamic update modes, their network ACLs, and notification name server addresses. Unsigned primary zones outside catalogs can apply record additions and updates to TTL, disabled state, comments, and expiry. `expiryTtl` sets a lifetime in seconds, with zero disabling expiry. Reapplying an unchanged live record keeps its existing expiry deadline. An NS record can declare IPv4 and IPv6 glue addresses in `glue`. An empty array clears the addresses. In-zone apex name servers use separate A or AAAA records. Changes advance the SOA serial and preserve generated and DHCP-maintained records. A manifest may include one enabled apex SOA record with no expiry. It can set the name server, responsible person, timers, TTL, and `useSerialDateScheme`. With the date scheme disabled, a serial higher than the current value advances the serial to that value. A zero serial uses the server’s normal serial generation. Omitting the SOA preserves it. Once the manifest owns the record collection, omitting an individual record removes it. An empty array or null clears the managed collection. DNS UPDATE requests are refused while the collection is managed. Changes to signed zones are pending. Other unsupported declarations return an error before producing a preview.

TSIG preview uses `dns.tsigKeys`. A new key requires an algorithm and a secret reference that resolves to nonempty base64. Existing keys retain omitted fields. A null entry previews removal, and a null map previews clearing the operator keys. The cluster catalog key is reserved. Standalone servers can apply these changes without restarting DNS. The server rejects removal of a key still referenced by a zone and prevents conflicting settings writes and backup restores while keys are managed.

Primary-zone `transfer.tsigKeys` lists canonical names of TSIG keys in the effective DNS configuration, including keys added in the same manifest. An empty list or null clears the references. Export includes the names and reports TSIG secrets separately as missing inputs. A manifest can remove a key and its primary-zone transfer references in one apply. A key still referenced by any effective zone policy cannot be removed.

Primary-zone `updates.securityPolicies` maps TSIG key names to owner names and allowed record types. Use `@` for the apex. Unmentioned keys and owners stay in place. Set a key or owner to null to remove that entry, or set the whole field to null to clear the policies. A referenced key must exist after apply. These policies constrain DNS UPDATE for zones whose record collections remain editable.

Explicit `allowZones` and `blockZones` apply live on standalone servers and on the cluster Primary. Each declared array replaces its entire list, and an empty array or null clears it. Names are canonicalized and deduplicated. An IP address selects its reverse DNS name. Allow rules still take precedence over block rules. The settings API and backup restore reject changes to a list while the manifest owns it. On a cluster, all peers must advertise support before the Primary changes either list or its ownership. Secondaries inherit the lists and ownership through cluster sync. Omit a list from the Primary manifest to release its ownership and retain its current contents.

The cluster Primary can manage authoritative defaults, update checks, EDNS UDP payload size, DNSSEC validation, EDNS Client Subnet, and application auto-updates. Changes to values or ownership require all peers to advertise declarative DNS policy support. Secondaries inherit these values and ownership through cluster sync and retain them when applying node-local settings. Omitting a previously managed field on the Primary releases its ownership and retains the last value.

The Primary can also manage `dns.recursion`, `dns.blocking`, and `dns.forwarding`. Changes and ownership releases for those sections require declarative resolver policy support from every peer. Applying a node-local manifest on a Secondary preserves the inherited policies. Changes to blocking policy preserve any temporary blocking pause.

The Primary can manage `dns.rateLimits` for the cluster. Each peer must support declarative rate limits before the Primary changes the limits or their ownership. Secondaries apply the tables, sample window, truncation percentage, and bypass networks through cluster sync. Omitting `dns.rateLimits` releases ownership and keeps the current settings.

The Primary can manage `dns.proxy` when every peer supports declarative proxy settings. Set the password using a secret reference on the Primary. The configured proxy and its ownership transfer to Secondaries, and exports mark the password as a missing input. Cluster API connections use the configured proxy. Keep peer addresses reachable through it or include the cluster domain and peer IP addresses in the proxy bypass list. Omit the proxy section to release ownership and retain the active settings.

The Primary can manage `dns.tuning` when every peer supports declarative DNS tuning. When a change needs a DNS listener restart, each Secondary rebinds its existing local endpoints before saving the transferred settings. A failed rebind or save restores the previous listener tuning and the Secondary retries the transfer.

The Primary can manage `dns.tsigKeys` when every peer supports declarative TSIG. Secondaries receive the effective keys and ownership through cluster sync. Release any existing local TSIG manifest ownership on a Secondary before it can inherit the Primary policy. The catalog key stays under cluster control, including when `dns.tsigKeys` is null. Omit `dns.tsigKeys` to release ownership and retain the current keys.

The Primary can manage `auth.ldap` when every peer supports declarative LDAP. Secondaries inherit the LDAP configuration and field ownership through cluster sync. Release any existing local LDAP ownership on a Secondary before it inherits the Primary policy. The Primary exports the effective settings and reports the bind password as a missing input. Omitting LDAP releases its ownership and preserves the current provider configuration.

The Primary can manage `auth.sso` when every peer supports declarative SSO. Secondaries inherit the provider settings and ownership. Enabling or disabling SSO, rotating the client secret, or changing the active provider configuration can restart each node's web service. Release existing local SSO ownership on a Secondary before it inherits the Primary policy. The Primary export includes SSO settings and marks the client secret as a missing input.

The Primary can manage `auth.groups` when every peer supports declarative groups. Secondaries inherit group definitions and manifest ownership. Group deletion still requires removing references, including zone grants retained on a Secondary. Release existing local group ownership on a Secondary before it inherits the Primary policy. Omit the section to release ownership while keeping the groups.

The Primary can manage `auth.users` when every peer supports declarative users. Secondaries inherit accounts and manifest ownership. Disabling an account revokes its interactive sessions. Deleting it also removes its retained zone grants. Release existing local user ownership on a Secondary before it inherits the Primary policy. The Primary export reports passwords and TOTP enrollment secrets as missing inputs.

The Primary can manage cluster-wide grants in `auth.permissions` when every peer supports declarative permissions. Secondaries inherit grants and ownership while retaining local zone-specific grants. Release any existing local permission ownership on a Secondary before it inherits the Primary policy. Omitting `auth.permissions` releases ownership and keeps the current grants.

A cluster Primary can manage blocklist sources and update intervals. Changes require every member to advertise declarative blocklist support. Reapplying the same managed policy can proceed before heartbeats resume after a restart. While the Primary manages blocklist settings, joining nodes must advertise the same capability. The Secondary receives the settings and ownership through configuration transfer. Applying a local manifest on the Secondary preserves the inherited policy, and the next transfer can update or release it. File sources must be accessible at the declared path on each node.

DHCP apply supports live and startup reconciliation. The API requires DHCP Modify permission and also requires Delete permission to remove scopes. Enabled scopes must bind successfully before the server writes configuration. Scope files and DHCP ownership participate in the same rollback journal as DNS, web, and logging settings. The scope list reports managed paths. The scope API rejects creation, deletion, or renaming that conflicts with managed membership and rejects changes to managed scope options, address ranges, exclusions, and enabled state. Scope option and reservation edits are checked as a unit before changes are applied. Lease removal or conversion that would change a managed reservation is also rejected. A DHCP backup restore can update unmanaged values when the managed scope membership, options, and reservations match. A conflicting restore fails before any selected store is changed. Applying a manifest that omits these declarations releases ownership and retains the current scope configuration.

DHCP preview uses one captured lease state to compare changes and validate the detached candidate against the existing scope file format. A new exclusion cannot cover an active dynamic lease. The live scope and DNS records stay unchanged during preview.

Regular export includes configured DHCP scopes and reservations for callers with DHCP View permission. To migrate enabled scopes, the destination needs network interfaces that can serve their ranges. Active leases, interface bindings, and derived local DNS addresses stay out of the export. Applying the exported scope map retains scopes unique to the destination. To remove one of those scopes, declare its name with a null value. A null scope map removes all scopes on apply, subject to the active-lease check. Scopes with reservations that cannot be represented by unique Ethernet MAC addresses and in-range IP addresses are reported as missing inputs.

Standalone servers can preview, apply, and export LDAP settings under `auth.ldap`. Preview and apply require Administration Delete permission. Use an environment or file reference for `bindPassword`; export reports a configured password as a missing input. LDAP applies through the authentication store and takes effect for subsequent directory sign-ins. Local users keep their existing credentials. A group map entry names a local group in the effective configuration. Legacy edits and auth restores must preserve managed LDAP fields and declared group mappings. Omitting a declaration releases its ownership and retains its configured value.

Standalone servers can preview, apply, and export OpenID Connect provider settings under `auth.sso`. Enabling SSO requires an authority, client ID, and secret reference. Provider connection changes restart the web service while SSO is enabled. Scope lists retain the required `openid` and `profile` scopes. External group mappings can reference groups created in the same manifest. Exports list the client secret under `missingInputs`. Legacy edits and auth restores must preserve declared SSO fields and group mappings. Omitting a declaration releases its ownership and preserves its configured value.

Use `apps.packages.<name>.configuration` to configure an installed app on a standalone server or the cluster Primary. Supply native text, a secret reference, or a file reference in a local startup manifest. A null value clears the configuration if the app accepts it. An optional version must match the installed package. Preview reports changed paths. The app validates its content during apply, and the server attempts to reactivate the previous configuration if activation or persistence fails. Recovery restores the prior configuration file if initialization is interrupted. Standalone and Primary exports list installed app versions. Supply package sources and opaque configuration listed under `missingInputs`. A null configuration in the export preserves the absence of configuration even when the supplied ZIP contains a default. Secondaries get their app packages and configuration from the Primary. A package declaration owns the app’s presence. A declared version or configuration also suspends automatic and legacy package updates. Declared configuration rejects conflicting API writes and merged backup restores. Release ownership before a restore that deletes the existing apps directory. Omit the declaration to release ownership while keeping the app installed. A null package entry removes the named app and owns its absence. A null package collection removes all installed apps and prevents legacy installs until released. Removal requires Apps Delete permission. Recovery restores package files if removal is interrupted. To install a missing app, use a local startup manifest with a ZIP file under `source.file`. The server verifies the requested version and initializes the app with the declared configuration or the package default. A failed installation removes the partial app directory. For startup or live apply, use an HTTPS URL under `source.url`. Preview validates the URL. Apply downloads the package, follows HTTPS redirects, and verifies the requested version when one is declared. A failed download leaves the app absent and can be retried. If the declared version differs from the installed version, provide a replacement source. The server preserves the existing app configuration unless the manifest changes it and restores the previous package if the replacement fails. An already matching version does not trigger a replacement.

In a cluster, preview and apply require support from every member. Secondaries inherit the app packages, configuration, and ownership from the Primary. The Primary must have a stored ZIP for any installed app it manages. A transfer carries the managed ZIP even during incremental sync so a Secondary can recover a missing package. A Secondary keeps its local settings when app ownership changes. Release any pre-existing local app ownership before joining a Primary that manages apps. Omitting the app declaration on the Primary releases ownership on the Secondaries on their next successful sync.

An initialized cluster Primary can reconcile `cluster.heartbeatRefreshSeconds`, `heartbeatRetrySeconds`, `configRefreshSeconds`, and `configRetrySeconds`. A null value selects the corresponding default. The configuration refresh interval must exceed the heartbeat refresh interval. Apply writes the options to the existing cluster store and notifies secondaries through the existing cluster protocol. An interval value change requires every member to advertise declarative interval support at join or heartbeat. Older members and members without a successful capability check block the change before persistence. Explicitly declared options are managed on the Primary that applies the manifest. Conflicting legacy edits are rejected as a unit. Omit an option in a later apply to release ownership while keeping its current value. Release all cluster option ownership before replacing the cluster configuration from backup or deleting the cluster. On an initialized node, declare `cluster.domain` and `cluster.bootstrap.role` to assert the current topology. A matching assertion makes no topology changes. A mismatched domain or role rejects the manifest. To initialize a fresh Primary at startup, use a [cluster-only `technitium.json`](examples/cluster-primary.json) with `cluster.bootstrap.role` set to `Primary`, the cluster domain, and a non-empty `cluster.node.addresses` list. Configure web TLS first. You can include interval declarations in the bootstrap file. Startup binds its listeners before initializing the cluster, then journals the cluster configuration, intervals, ownership, DNS and authentication files, and both cluster zones. After a failed startup, correct the reported problem and retry with the same file. On a subsequent startup, a matching domain, role, and advertised addresses preserve the existing node identity. A fresh Secondary can join from a [cluster-only startup manifest](examples/cluster-secondary.json) with web TLS configured. Declare the cluster domain, advertised addresses, Primary HTTPS origin, username, and password reference. Use `primaryAddress` to reach the Primary before cluster DNS is available. The server verifies the remote role and cluster domain before registering. Join credentials are read only when joining during startup. A successful join records the advertised addresses as managed before startup finishes. The final membership, catalog, and ownership writes share a rollback journal. A matching initialized node can restart after the join secret is removed. If sync fails after registration, the server attempts to remove the incomplete membership. If cleanup cannot reach the Primary, remove the incomplete member there before retrying. A failed join can leave synchronized data on the Secondary. With Administration View permission, export includes the current cluster domain, local role, and advertised addresses. Primary exports include cluster intervals. Secondary exports include the Primary HTTPS origin and report the join username and password as missing inputs. To recreate a node on a fresh instance, configure web TLS, copy the exported `cluster` section into a cluster-only startup manifest, and supply the join inputs for a Secondary. On an initialized node, declare `cluster.node.addresses` to reconcile and manage its advertised addresses. A Primary applies the node addresses together with the matching A and AAAA records and the PTR records in locally hosted primary or forwarder reverse zones. A Secondary persists its addresses before scheduling publication to the Primary. If publication fails, the Secondary retries using the cluster configuration retry interval. A change made during publication schedules another update. The legacy address endpoint rejects conflicting edits until a later apply omits the declaration. An unclustered server with web TLS configured can also preview and apply a cluster-only Primary bootstrap manifest through the configuration API. Live bootstrap requires new cluster and catalog zones. Use startup bootstrap when adopting existing zones. An unclustered Secondary can also preview and apply a cluster-only join manifest with web TLS configured. Use environment references for join secrets in API requests. Preview validates local prerequisites and resolves the references without connecting to the Primary. Apply rejects a changed secret and verifies the Primary before registering. A Secondary retains the Primary’s advertised interval ownership separately from its own declared address ownership. Forced promotion keeps the last synchronized interval values and ownership. Before restarting a promoted node that uses a startup manifest, set its declared role to Primary and include the interval declarations it should keep managing. For graceful promotion between servers that support declarative handoff, the successor persists the final interval policy before requesting retirement of the old Primary. The old Primary checks the policy revision before retiring. For older servers, release ownership on the old Primary and reapply the interval declarations on the promoted node.

Declare local groups under `auth.groups` on standalone servers. A group can include a `description`, and the name matches existing groups case-insensitively. An LDAP mapping can refer to a group created by the same manifest. Use a null entry to remove an unreferenced custom group. A null group collection requests removal of all custom groups. Removal fails if a group is still referenced by a user, permission, or directory mapping. Built-in groups are preserved. Updating a description preserves membership and permissions. A named declaration owns the group’s presence or absence and any declared description. A null collection also prevents creation of custom groups. Legacy edits and auth restores must preserve owned paths. Group membership for individual users remains editable. Omitting the group declaration in a later apply releases its ownership.

On standalone servers, use `auth.users` to create local users and update display names, disabled state, session timeouts, group memberships, and passwords. A new user requires a password reference. An existing user keeps their password when the reference is omitted. Supply a password reference when changing the iteration count. A group declaration in the same manifest can supply a referenced group. Declaring a group list replaces the account’s existing memberships and retains Everyone. The built-in administrator must stay enabled and in Administrators. Exports list passwords and existing TOTP enrollment as missing inputs. Use a null user entry to remove an account and revoke its sessions and permission grants. A null user collection removes custom local accounts while preserving the built-in administrator and external-provider accounts. Accounts with legacy static or cluster sessions cannot be removed. Remove or reassign manifest-defined static sessions before or in the same apply that removes their account. The same apply can remove a group when it removes or updates its remaining members and clears other references. Deleting a zone also clears the grants scoped to that zone. Explicit user entries own account presence or absence and the fields they declare. A null user collection also blocks creation of custom local accounts. Conflicting admin, self-service, group membership, and auth restore changes are rejected. Omit a declaration in a later apply to release its ownership. A local account can set `totp.enabled` and supply `totp.enrollment` as a secret reference to a valid `otpauth://totp/` enrollment URI. Enabling TOTP requires enrollment material. Set `enabled` to false to disable TOTP, and set `enrollment` to null to clear the key. Omitted TOTP fields retain their current values. Exports include the enabled state for enrolled accounts and list the key under `missingInputs`.

On standalone servers, set an account’s `type` to `RemoteLDAP` or `RemoteSSO` to provision it before its first directory sign-in. SSO accounts require a unique `externalIdentifier`. LDAP uses the account name. Both use provider credentials. Group declarations are supported when the provider does not map local memberships. An explicit null entry can remove a provider account. A null user collection still preserves provider accounts.

On standalone servers, declare section-level grants under `auth.permissions.<section>.users` or `.groups`. Each entry sets the principal’s View, Modify, and Delete flags. A null entry removes that grant. A null section or permissions collection restores fresh-server section defaults. The manifest can create the referenced principals in the same apply. The mandatory administrative grants are preserved. Named grants own their declared flags or absence. A null section or collection owns the reset grants. Legacy permission edits, principal changes, and auth restores must preserve those grants. Omit the declaration to release ownership. Use `zones.<name>.permissions` for grants on a primary zone outside catalogs. Zone grants use the same named maps. A null zone permissions value clears custom grants and retains the required Administrators and DNS Administrators grants. Zone permission ownership protects legacy edits and auth restores.

Use `auth.staticSessions.<name>` to configure a node-local API credential for an existing or simultaneously declared user. Supply a unique 64-character token through an environment reference or a file reference in the startup manifest. Only the reference is persisted. Reapplying a changed reference value rotates the active token. A null entry removes that session, and a null collection removes all manifest-defined static sessions. Legacy environment sessions retain their existing configuration. Exports list each token under `missingInputs`.

## Exporting supported settings

Run `dotnet run --project DnsServerApp/DnsServerApp.csproj -- config export https://dns.example.test > technitium.json` with the same token. The command writes stable manifest JSON for fields supported by apply and reports the partial export on standard error. Use `--include-preview-only` after the server URL to include additional fields for inspection. The server reports omitted inputs by manifest path, and the CLI prints those paths on standard error. These include configured proxy and certificate passwords, TSIG secrets, blocklist source URLs, and forwarder lists containing DoH URLs with query strings, user information, or fragments. Keep the JSON output as the manifest and supply the listed inputs separately during migration. The CLI requires a server with the configuration export endpoint.

Regular export includes unsigned primary zones outside catalogs and cluster infrastructure, including node-local zones on clustered servers. Callers need Zones View permission for the section and each included zone. The export includes supported policies and operator records. Export includes the apex SOA settings and serial date scheme with a serial of zero, so a new instance generates its own serial. Generated name server records, DNSSEC records, and DHCP-maintained records are omitted. If a record collection contains data or metadata that apply cannot reproduce, the export lists the collection in `missingInputs`.

To reproduce the exported settings, validate the file, preview it against the destination, then apply using the destination revision. Check the declared DNS listener addresses and log directory against the destination host before applying.

## Applying DNS, web, logging, and blocklist settings

Run `dotnet run --project DnsServerApp/DnsServerApp.csproj -- config apply path/to/technitium.json https://dns.example.test <revision>` with the revision printed by `config plan` and a token with Settings modify permission. Generate a new preview if the revision becomes stale.

This implementation applies `dns.serverDomain`, `dns.localEndpoints`, the IPv4 and IPv6 `dns.sourceNetworks` lists, the three `dns.authoritative` record TTL defaults, SOA serial format, minimum SOA refresh and retry intervals, SOA responsible person, zone-transfer and NOTIFY network allowlists, `dns.checkForUpdates`, `dns.ipv6Mode`, `dns.udpSocketPool.enabled`, `dns.udpSocketPool.excludedPorts`, `dns.udpPayloadSize`, `dns.dnssecValidation`, `dns.clientSubnet`, `dns.recursion`, `dns.cache`, `dns.blocking`, `dns.forwarding`, `dns.rateLimits`, `dns.tuning`, `web.realIpHeader`, `web.frameAncestors`, `web.reverseProxyAcl`, `logging.destination`, `logging.folder`, `logging.noStackTrace`, `logging.retentionDays`, `logging.useLocalTime`, `logging.ignoreResolverLogs`, `logging.logQueries`, `blocklists.sources`, `blocklists.updateIntervalHours`, `statistics.inMemory`, `statistics.retentionDays`, and `apps.autoUpdate` together. EDNS Client Subnet, recursion, blocking, forwarding, query-rate limits, DNS tuning, and app auto-update can be applied on standalone servers. Recursion ACLs preserve rule order. Forwarding preserves list order and the transport of each server. Exports omit the forwarding server list if a DNS-over-HTTPS endpoint contains user information, a query string, or a fragment. Temporary blocking pauses affect live DNS and are excluded from the persisted blocking policy and export. Release recursion, blocking, forwarding, query-rate limits, DNS tuning, and cache policy ownership before restoring a legacy combined DNS backup. A zero cache prefetch trigger disables prefetch. Enabling prefetch with the trigger omitted resets an existing zero trigger to 9. Preview includes these implied changes, while ownership follows the fields declared in the manifest. A manifest that explicitly enables prefetch and sets its trigger to zero is invalid. A Client Subnet host-address override uses the effective prefix for its IP family. The server domain, authoritative defaults, update checks, EDNS UDP payload size, DNSSEC validation, and blocklist settings can be applied on standalone servers. Other declarations are rejected before mutation. The server persists the values and their ownership in `dns.config`, `log.config`, `webservice.config`, and `blocklist.config`. A failed DNS bind restores the previous listeners and rejects the apply. Applying a manifest that omits a previously managed field releases ownership and keeps the current value. The Settings screen displays managed manifest paths for the selected server. The settings API returns the same paths in `managedSettings`. Settings edits and backup restores that would change an owned value are rejected before other settings in the request are changed. If a backup uses a combined configuration format whose listener values cannot be verified (versions 6–27), release DNS listener ownership before restoring it. Combined backup versions 2–27 require releasing IPv6 mode and UDP excluded-port ownership before restore. For UDP port exclusions, an empty list clears all exclusions and `null` selects the effective web TLS port. Combined backup versions 23–27 require releasing ownership of the default record TTL before restore. Combined formats leave the separate NS and SOA TTL defaults unchanged. DNS settings backups can be restored when their statistics and DNS query or resolver logging values match the manifest-managed values. Release ownership of those fields before restoring a legacy combined DNS backup. Release ownership of the blocklist sources and update interval before restoring DNS settings from a combined backup. Versions 25–27 require releasing ownership of the UDP payload size before restore, and versions 26–27 require releasing ownership of DNSSEC validation.

The reverse-proxy ACL uses first-match rule order. An empty array trusts no IP-based proxies, while `null` restores the server’s default ACL.

### Startup

Place `technitium.json` in the server's configuration directory to reconcile the supported DNS, web, logging, statistics, blocklist, and DHCP settings at startup. The console host and Windows service both use this path. Startup rejects invalid manifests and unsupported sections before opening listeners. On standalone servers, `web.localAddresses`, `web.httpPort`, `web.tlsPort`, `web.tlsEnabled`, `web.http3Enabled`, and `web.redirectHttpToTls` can be applied at startup. Enabling TLS requires an existing certificate configuration. Enabling HTTP/3 requires TLS and host QUIC support. The server binds the declared web and DNS listeners before committing values and ownership. Cluster nodes can also declare their local HTTP port, shared bind addresses, HTTP and HTTPS Unix sockets, HTTP/3, and HTTP-to-TLS redirect. Candidate bind addresses must cover the current and declared cluster addresses. Web TLS must stay enabled. Changing shared bindings preserves the current TLS certificate so peers can continue to authenticate it. Cluster nodes can declare a new fixed HTTPS port. Apply commits the listener and advertised URL together. A Secondary publishes the URL to the Primary through the existing retry path. A Primary also updates the signed TLSA records for the new port and notifies its Secondaries. A Secondary refreshes the signed cluster zone when it learns of a port change. If it misses the notification while offline, the Primary detects the stale endpoint at the next successful heartbeat and notifies it again. Cluster nodes can also declare a replacement web certificate. The Primary updates its signed TLSA record in the same transaction. A Secondary publishes its committed certificate to the Primary. Secondaries refresh the signed cluster zone on notification or after a failed connection to the Primary. The web HTTP and HTTPS Unix sockets require an absolute path when enabled. Applying a managed socket path preserves any file already at that path and reports a bind failure. Live apply returns an operation ID when the web service must restart. Use `config status <server-url> <operation-id>` on the new origin after a successful rebind or on the original origin after rollback. For automation, add `--wait <result-url>` to `config apply`. The command checks both the supplied result origin and the original origin for up to 45 seconds and returns a failure exit code on rollback or timeout. Use the original origin as the result URL if it will stay the same.

The startup file takes effect again at the next restart. Update that file when changing the desired startup settings. With no startup file, the server continues with persisted values and ownership. To release all managed settings, apply or start with a manifest containing only `schemaVersion`.

If the process stops during manifest persistence, the next startup restores the previous DNS and logging configuration and ownership before loading settings. Startup then reconciles the startup manifest if one is present.
